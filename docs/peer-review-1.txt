2. Initial Understanding
What the project does. DropShelf is a storefront that lets an independent creator publish a profile page, list products, and take real payments through Stripe Checkout without going through a marketplace. It's a single Next.js App Router app backed by Postgres (Neon) through Drizzle ORM, and Stripe is the only external service.

Who it supports. Two different audiences, and the repository is clear about the split. There's a public buyer who browses and purchases without signing in, and a signed-in admin who manages the catalog and can cancel orders. docs/sprint-4-quality/user-action-diagram.md makes this explicit by giving each one its own sequence diagram.

Primary workflow currently implemented. A buyer loads /, the server component queries the products table, the buyer clicks Buy, and createCheckoutSession() in lib/actions.ts looks the product up in the database and creates a Stripe Checkout Session carrying productId, quantity, and unitPriceInCents in metadata. After payment, two independent things happen. The buyer gets redirected to /checkout/success?session_id=, which re-verifies the payment against Stripe instead of trusting the redirect, and Stripe asynchronously POSTs checkout.session.completed to /api/webhooks/stripe, which writes the orders and order_items rows. Sprint 4 added an authenticated admin surface on top of that: product create/edit/archive at /admin/products, plus an order cancel-and-refund action on /orders.

What was hard to figure out. Not much about intent, since the README is unusually complete. The one thing I couldn't work out from the top-level README was how to configure authentication, because the root README's environment block is out of date (see §4). I had to open prototype/README.md to find the Clerk variables. I also couldn't tell what the current system looks like from the three required deliverable files (docs/architecture.md, docs/manual-verification.md, docs/ai-implementation-review.md), because all three are pointer files that still name Sprint 3 as authoritative. More on that in §5.

9. Engineering Strengths
Strength 1: the webhook's idempotent, atomic single-statement write.

What I observed: app/api/webhooks/stripe/route.ts:55-65 writes the orders row and its order_items row in one parameterized SQL statement, using a WITH inserted_order AS (INSERT ... ON CONFLICT (stripe_checkout_session_id) DO NOTHING RETURNING id) INSERT INTO order_items ... SELECT ... FROM inserted_order CTE, rather than two sequential db.insert() calls.

Evidence: the code itself, the reasoning comment at lines 49-54, the design note at docs/sprint-3-persistence/updates/webhook-atomic-write.md, and a test asserting a redelivered webhook doesn't double-insert.

Why it improves the project: payment webhooks get retried by design. Stripe redelivers on non-2xx responses and occasionally duplicates, so a naive handler produces either duplicate orders or orphaned rows, and both corrupt financial records. This handles both hazards at once. ON CONFLICT DO NOTHING makes redelivery a complete no-op, because an empty CTE means the order_items insert selects from nothing, and running as a single statement removes the crash window between the two inserts. What makes it more than a lucky idiom is that the constraint behind it, neon-http having no transaction support, is written into the comment. The next person to touch this knows why db.transaction() wasn't used and won't "simplify" it back into a bug.

Strength 2: authorization enforced at the action boundary, not only at the route boundary.

What I observed: every mutating server action calls requireAdmin() independently. That's products-actions.ts:11, 28, 44 and orders-actions.ts:11, even though proxy.ts:3-8 already protects /admin(.*) and /orders(.*). app/orders/page.tsx:9 does the same.

Evidence: the call sites above, the rationale in prototype/README.md:71-73 ("Server Actions are reachable even when their page isn't rendered"), and the origin story at docs/sprint-4-quality/kickoff.md:7, where live testing surfaced the gap.

Why it improves the project: Next.js Server Actions are POST endpoints with generated ids, and you can invoke them directly without ever loading the page that renders them. A project that gates only in middleware has an authorization hole that clicking through the UI will never reveal. Enforcing at both layers means a future refactor of the route matcher, or a Clerk API change like the one this project already absorbed, degrades safely instead of silently exposing every mutation. The redundancy also wasn't theoretical caution. It came out of a near-miss and then got written down so the next person understands why it looks redundant. The test discipline backs it up too: products-actions.test.ts asserts each action calls requireAdmin() and rejects invalid input before touching the database, so a regression fails the suite instead of shipping.

Why it matters: these are the exact paths a reviewer, a grader, or a new engineer opens first. Right now they describe a system one sprint behind the code, so the project's most impressive work (the auth migration, full CRUD, the refund compensating transaction) is invisible at the front door. Worse, the architecture doc actively lists a solved problem as an open question.

Scoped next step: create docs/sprint-4-quality/architecture.md by copying the Sprint 3 document and editing three sections. The proxy.ts component description, the route table, and a new "Admin surface" section covering lib/admin.ts, lib/products-actions.ts, and lib/db/validation.ts. Then update the three stubs to say "Current (Sprint 4)". The Sprint 3 document is well-structured enough that this is an edit, not a rewrite.

Recommendation 2: make requireAdmin() check identity, not just authentication.

The issue: lib/admin.ts:3-9 treats any signed-in Clerk user as an admin. It only checks that userId is non-null. prototype/README.md:60-62 acknowledges this ("any signed-in user counts as admin") on the premise that there's exactly one account and no public sign-up. But docs/sprint-4-quality/kickoff.md:7 says disabling public sign-up is still open.

Evidence: those two files read together, plus the blast radius. orders-actions.ts:35 calls stripe.refunds.create(), and products-actions.ts:43-53 can archive products out of the storefront.

Why it matters: Clerk instances allow public sign-up by default. Until that setting changes, the documented security model and the deployed one disagree, and the gap isn't read-only. A self-registered account reaches real Stripe refunds. This is a configuration state rather than a code bug, which is exactly the kind of thing that's easy to leave undone.

Scoped next step: two small changes, either of which closes it. Disable public sign-up in the Clerk Dashboard, which is already planned, and add a defense-in-depth check in code. Compare userId against an ADMIN_USER_ID environment variable, or check a Clerk publicMetadata.role === "admin" claim, so the code enforces the invariant the README already asserts instead of depending on a dashboard toggle staying flipped. __tests__/lib/admin.test.ts already mocks the Clerk boundary, so a "signed in but not the admin" rejection test costs a few lines.

Question 3: What happens to a refund if the status update fails?

orders-actions.ts:35-40 issues the Stripe refund and then writes status: "refunded". Since the double-refund guard at line 17 reads that same status, a failure in between leaves an order that's been refunded at Stripe but is still eligible to be refunded again. Was this considered and accepted as acceptable risk for the current scope? The webhook path solved the identical two-system-consistency problem carefully, as I described in §9, so I suspect this is a scope call rather than an oversight. But it isn't written down anywhere, and a short note in the Sprint 4 architecture's "Deviations" section would turn it into a documented decision instead of an apparent gap. If you wanted to close it cheaply, reversing the order would help: mark the row "refunding", call Stripe, then mark "refunded". That makes the failure mode visible instead of silent.

12. Final Reviewer Summary
DropShelf handles the hard parts well. The Stripe webhook is repeatable and atomic under redelivery through a single CTE statement, with the constraint that forced that design recorded in a comment so it survives future refactoring. Authorization is enforced at both the middleware and the individual server-action boundary, a distinction found through live testing rather than assumption. Validation is derived from the schema so it can't drift. The 56-test suite leans toward the failure cases that actually matter, like unverifiable signatures, duplicate deliveries, missing metadata, and double refunds, and it comes with a justified statement of what's deliberately not tested. The documentation. Each sprint's architecture ends with open questions and the next sprint closes them.

The most important risk isn't in the code, it's in the map. All three course-required documents still declare Sprint 3 authoritative, and the Sprint 3 architecture describes an authentication mechanism the code replaced, so the repository's front door understates the project by a full sprint. Second to that, requireAdmin() currently grants admin access to any signed-in user while public sign-up is, by the project's own status note, still enabled. That's a small configuration gap with a real blast radius, since the admin surface issues Stripe refunds.

Could another engineer understand, run, verify, and continue this project? Run, yes, but only after finding the Clerk variables in README.md, because the root README's environment block is stale. Verify, yes. The automated suite is real and the Sprint 3 manual verification checks database state rather than just HTTP responses, though the Sprint 4 admin flows are still automated-only pending the Clerk account creation the student has already flagged.
